Agent 能力扩展渐进式披露知识打包

一概念的个人解释

我对 Skill 的理解：Skill 是把"某类任务该怎么做"从聊天提示词里搬进文件系统，按需加载的一包专业知识。

过去我们让模型掌握某个流程（比如"怎么规范地生成 Excel 报表"），靠的是把一大段指令写进系统提示——不管今天用不用得上，这段指令都常年占着上下文。Skill 的思路完全不同：把这类知识写成一个文件夹（核心是一份 SKILL.md，带 YAML 元数据声明它"什么时候该被想起"），平时只在上下文里留一行元数据；只有当任务真正匹配时，模型才把正文读进来。

我觉得最贴切的类比是新员工的岗位手册：公司不会第一天就把所有岗位的操作手册背给新人听，而是在新人接手某类任务时说"这种情况去查《报销手册》第 3 章"。Skill 里的 name/description 就是手册目录上的标题，正文是操作步骤，附属脚本和参考文件是手册的附录。这个设计还有一个妙处——知识可以被普通人编写和分享：写好一个 Skill 不需要写代码、不需要改模型，就像写一篇带目录的文档一样。

二核心机制或组成

2.1 标准结构：一个文件夹

my-skill/
├── SKILL.md          # 核心：YAML 元数据 + 操作说明正文
├── references/       # 附属参考文档（按需读取）
├── scripts/          # 可执行脚本（如格式转换、校验工具）
└── assets/           # 模板、示例等静态资源

2.2 渐进式披露（Progressive Disclosure）——Skill 的灵魂

  • 第一层（始终加载）：只有 name 和 description 两个元数据字段进入系统提示，几乎不占空间，作用是让模型在成百个技能中"判断该用哪一个"；
  • 第二层（匹配时加载）：任务命中后，模型读取 SKILL.md 正文，获得操作流程；
  • 第三层（需要时加载）：正文里引用的参考文档、脚本、资源，只在具体步骤需要时才读或执行。

这个三层结构解决了"知识全面性"与"上下文经济性"的矛盾：知识可以写得非常详尽，但任何时候只支付当前需要的那部分上下文成本。

2.3 触发与执行

匹配靠 description 写得准——它相当于技能的"触发条件声明"；执行则由模型按 SKILL.md 正文中的指令走，包括调用技能自带的脚本。Skill 已形成开放标准（agentskills.io），由文件夹 + SKILL.md 的约定构成，可跨支持的智能体平台复用。

三一个具体应用场景

场景：智能体处理一份 PDF 表单提取任务。

用户上传一份 200 页的 PDF，要求"把每章的表格提取出来整理成 Excel"。智能体的动作序列：

  1. 触发：模型在已安装技能列表中看到 pdf 技能的描述——"处理 PDF 的读取、拆分、合并、表单与表格提取"，与当前任务匹配，决定加载；
  2. 读取正文：读入 SKILL.md，了解到处理 PDF 应优先使用某几个 Python 库、拆分与提取的标准做法、常见报错的处理方式；
  3. 按需深入：正文提示"表单字段提取详见 references/forms.md"，模型按指引读取该参考文档；
  4. 执行脚本：按文档建议运行技能自带的提取脚本，输出表格数据；
  5. 完成任务：整理为 Excel 并交付。

整个过程里，只有这条 PDF 任务链路的知识被加载了——同会话中其他几十个技能（写作、图表、部署……）始终只占一行元数据的空间。这正是"写一次，处处按需用"的价值。

四容易混淆的问题或使用边界

易混淆对象关键区分
Skill vs 工具/MCP工具/MCP 是"手"——提供模型原本没有的能力接口（查天气、连数据库）；Skill 是"操作手册"——教模型如何组合已有能力做好一类事。二者互补：Skill 常在正文中调用工具或脚本。
Skill vs 系统提示系统提示每次请求全量加载，适合少量全局规则；Skill 按需加载，适合大量、分领域、低频使用的流程知识。把所有知识堆进系统提示是 Skill 要解决的经典反模式。
Skill vs AgentAgent 是有自主循环的执行者；Skill 是静态的知识包。Agent 可以"装"很多 Skill，Skill 本身不会自己运行。

使用边界与注意事项

  • description 是唯一触发入口：写得含糊就永远不会被选中，写得过宽又会被频繁误触发——Skill 的实际效果很大程度取决于这一行字的质量；
  • 只装不用 ≠ 安全：第三方 Skill 的脚本在被触发后是以你的权限运行的，安装前必须审查其内容（这正是很多平台要求安装前审计的原因）；
  • Skill 不是万能容器：需要实时外部数据或新能力的场景该用工具/MCP；纯粹一次性的小任务直接写提示词即可，没必要打包成 Skill；
  • 粒度要合适：一个 Skill 对应一类任务，不要把不相关的流程塞进同一个 SKILL.md，否则正文冗长、加载浪费。
