LLM 原理上下文工程记忆与检索

一概念的个人解释

我对上下文的理解：上下文就是模型在生成这一刻"能看见的全部世界"。

大模型本身没有真正的长期记忆——两次对话之间，它不会"记得"你说过什么。它每次回答，都是从一套当场提供给它的材料出发的：系统指令、聊天历史、检索来的资料、工具返回的结果……这些材料打包在一起，就是上下文。

我喜欢把它比作一张桌面：模型像个坐在桌前的分析师，桌面面积有限（上下文窗口），它只能基于摊在桌上的文件做判断。桌上没有的东西，它就"不知道"；桌上的东西太多太乱，它也会顾此失彼。所以"上下文工程"（context engineering）的本质不是往桌上拼命堆资料，而是做减法和排序：在有限的桌面面积里，只放当下最高信号量的内容。很多人以为模型能力强弱全看模型本身，实际使用中，"桌上摆了什么"往往比"分析师多聪明"更影响输出质量。

二核心机制或组成

2.1 上下文由什么构成

  • 系统提示（System Prompt）：设定角色、规则、行为边界，位于最前部，权重通常最高；
  • 对话历史：此前的多轮问答，让模型"接得上话"；
  • 检索内容（RAG）：为回答当前问题临时检索到的文档片段；
  • 工具调用与返回结果：Agent 循环中每次工具执行的输入输出；
  • 用户当前输入：正在处理的那条消息。

以上所有内容都被切成 token 排成一个序列送入模型——模型看到的是这一个序列，而不是它"存储里的知识库"。

2.2 关键约束：窗口大小与注意力预算

  • 上下文窗口：序列有长度上限，超出就必须丢弃或压缩早期内容。
  • 注意力预算：即使窗口够大，模型对长序列的注意力也不是均匀的——中间部分的内容更容易被"忽略"（业界常称 lost in the middle 现象）。所以关键信息应放在开头或结尾，且总量要克制。
  • 成本与延迟：上下文越长，每次请求的 token 费用和响应延迟越高，"塞满窗口"是既昂贵又低效的做法。

2.3 主流管理策略

  • 压缩/摘要：长对话定期总结成要点，用摘要替换原始历史；
  • 结构化记忆：把需要跨会话保留的信息写入外部文件（如 MEMORY 文件），需要时再读入；
  • 即时检索（just-in-time context）：不预先把资料塞进上下文，而是像 Agent 那样按需检索、按需读文件，用"文件路径 + 按需读取"换取上下文的高信号密度；
  • 子任务拆分：把超大任务交给多个子智能体，各自维护独立上下文，只回传结论。

三一个具体应用场景

场景：一个每天连续工作数小时的长会话编程助手。

用户从上午开始让助手重构一个中型项目。到下午，原始对话历史加上反复读过的代码早已远超窗口上限。助手是这样管理上下文的：

  1. 压缩历史：把上午的几十轮交互压缩成一份摘要（"已完成：数据层重构；遗留：测试未更新"），替换原始记录；
  2. 写入记忆：把项目约定（如"所有函数必须有中文 docstring"）写入一个持久记忆文件，而不是反复占用对话空间；
  3. 按需读文件：不一次性读入整个代码库，而是先看目录结构，只把当前要改的两三个文件读进上下文；
  4. 即时丢弃：一个子任务完成后，其大段中间产物（原始报错、旧代码）即从工作上下文中移除，只留结论。

效果：模型"感觉上"始终记得整个项目的历史，但桌面上永远只摊着当前任务最需要的几张纸。这就是上下文管理在真实产品中的运作方式。

四容易混淆的问题或使用边界

易混淆对象关键区分
上下文 vs 记忆上下文是"本回合可见的输入"，用完即弃；记忆是"主动留存的长期信息"，必须显式写入外部存储，下次再取回上下文。会话中模型"记得"前文，只是因为前文还在上下文序列里。
上下文 vs 模型知识模型在训练中学到的参数化知识不受上下文控制；上下文提供的是"开卷资料"。模型可能把两者混淆——把上下文里的内容当成自己的知识，也可能反过来忽略上下文而依赖先验，这正是提示工程要处理的。
上下文 vs 数据库/RAGRAG 是给上下文"供货"的手段，不是上下文本身；检索质量差，上下文就差。

使用边界与常见误区

  • 窗口大 ≠ 应该塞满：百万 token 的窗口不等于可靠的处理能力，长上下文中段的召回率会明显下降，重要内容要前置并做结构化组织；
  • 上下文 ≠ 真相保证：往上下文里塞错误或互相矛盾的信息，模型可能照样采信或纠缠其中——"垃圾进，垃圾出"；
  • 上下文 ≠ 安全容器：任何进入上下文的外部内容（网页、工具返回）都可能影响模型行为，长上下文也带来提示注入风险，敏感操作必须有独立校验，不能依赖"上下文里写了规则"来保证安全。
