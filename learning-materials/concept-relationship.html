〇一句话总览

Agent 是动手干活的执行者，上下文是它每一步决策所依据的"工作现场"，而 Skill 是提前存放在档案室里、到现场才被取用的"任务操作手册"。三者是执行 — 供给 — 沉淀的关系。

二上下文如何影响 Agent 的工作

Agent 的每一次"决策下一步"都不是凭空发生的，而是对上下文的一次读取。上下文的状态直接决定了 Agent 表现的上限：

上下文状态对 Agent 工作的影响典型对策（上下文工程）
信息缺失
（桌上没有那份文件）		 Agent 不知道关键约束或现状，决策建立在想象上，产生幻觉式行动；或者反复向用户追问。 即时检索（just-in-time）：先列目录再按需读文件；用工具查询而不是靠参数化知识猜。
信息过载
（桌面堆满资料）		 超出窗口上限导致早期内容被截断；即使没超限，注意力预算被稀释，中段的关键指令容易被忽略，Agent 变得"健忘、走神"。 压缩/摘要历史；任务结束即丢弃大段中间产物；关键规则前置并结构化。
信息劣质
（桌上的文件是错的）		 工具返回的错误结果、互相矛盾的内容会被 Agent 当作事实采信，错误沿着循环逐步放大。 对工具输出做校验步骤；为易错环节配置评估-重试的工作流模式。
信息有序且高信号
（桌面整洁、文件在手）		 Agent 每一步决策都有充分依据，循环更短、路径更准、成本更低——这是 Agent 可靠运行的前提。 结构化记忆、按任务分层组织上下文、Skill 按需注入（见下节）。

一句话：Agent 的智能是模型给的，但 Agent 的可靠是上下文给的。同一个模型，上下文管理得好坏可以直接决定任务成败。

三Skill 如何沉淀可复用的任务知识

Skill 解决的是上下文的一个根本矛盾：知识要全才可靠，上下文要省才高效。它的沉淀机制可以拆成三步：

阶段发生什么上下文代价
① 编写沉淀 把某类任务的成功做法（流程、规范、易错点、可用脚本）写成文件夹：一份带 name/description 的 SKILL.md，加参考文档和脚本。知识就此"固化"在文件系统里，不依赖任何一次对话。 0（存在磁盘上，不进上下文）
② 触发供给 Agent 接到新任务时，扫描所有 Skill 的元数据（这一行描述常驻上下文）；description 与任务匹配 → 读入正文；正文引用的参考/脚本再按需加载。 渐进式支付：一行元数据 → 一篇正文 → 需要的附录，任何时刻只为当前需要付费
③ 使用与回写 Agent 按 Skill 指令执行任务；任务完成后，若发现更好的做法或新的坑，可修订 SKILL.md——知识完成一次迭代，下次同类任务直接受益。 任务结束即可从上下文中丢弃，知识已在文件中续存

SKILL.md（做法+规范+易错点）"]

这条"经验 → 文档 → 触发 → 复用 → 迭代"的环，正是 Skill 与普通提示词的本质区别：提示词的生命周期是一次对话，Skill 的生命周期是所有未来的同类任务。

四三者职责与关系对照表

维度 🤖 Agent 🧠 上下文 📦 Skill
角色类比被授权的员工员工手边的办公桌档案室里的操作手册
本质模型 + 循环 + 工具的执行系统模型当前可见的全部输入序列文件系统中的结构化知识包
生命周期与任务等长，随任务启停与单次请求等长，用完即弃长期存在，跨任务、跨会话复用
回答的问题"这件事由谁做、怎么做""此刻依据什么来做""以前这类事是怎么做成的"
彼此关系消费上下文做决策；触发并执行 Skill是 Agent 的决策依据；是 Skill 知识的"卸货区"按需向上下文供给知识，约束 Agent 的行为路径
缺了会怎样—（三者缺一即不成立）Agent 无依据决策，等于盲走每次同类任务从零摸索，重复消耗上下文与人力

五一个串起来的完整例子

用户对智能体说："帮我把这份 200 页的 PDF 里的表格整理成 Excel。"
  1. Agent 开始循环：解析目标 → 检查技能元数据，发现 pdf Skill 的描述与任务匹配；
  2. Skill 被触发，操作知识注入 上下文——用什么库、怎么处理表单、哪里容易踩坑，无需 Agent 自己重新摸索；
  3. Agent 基于这些知识执行：调用提取脚本、逐章处理——每一步的中间结果又回填进 上下文；
  4. 200 页的内容远超窗口，上下文管理介入：逐章处理完即压缩丢弃中间产物，只保留结论；
  5. 任务完成；若过程中发现了新的更优做法，Agent（或人）把经验回写进 Skill，完成一次沉淀。

这个例子中：Skill 决定了 Agent "会不会做"（知识供给），上下文决定了 Agent "能不能持续做对"（信息供给），而 Agent 是把两者串成闭环的执行主体。
